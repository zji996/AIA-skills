# 模型界面设计

模型看到的每一段文字、每一个工具结果都是界面。目标：在不增加步数、不制造无效步的前提下，让模型自己判断下一步。下面每条先写原则，再写怎么检查。

## 1. 渐进式披露

先给能做决定的一层，细节按需取；每层结果的末行说明下一层怎么拿。

- 常见分层：索引或摘要 → 单项全文 → 局部放大。例：Skill 先只给名称与一句描述，用时再读正文；图片先给尺寸与草图，框选后给局部原图；多页文档先给目录，按页号读全文。
- 一层就够时直接给全，不为分层多一步：只有一页、内容很短、或几乎每次都要全文的，第一层就给全文。
- 分层的回报在长对话里最大：每一步请求都会重发之前的结果，第一层越小，之后每步越省。
- 检查：列出典型任务，逐个数「现在几步 / 分层后几步」。分层只能让少数任务多一步，且要换来之后每步明显更少的重发量。

## 2. 结果带着下一步

模型下一步大概率要的东西，直接放进这一步的结果。

- 例：写入后附上生成的预览图，不让模型再读一次；读图结果写明原图尺寸与可用的放大方式；越界错误给出可用范围；参数写错时给出正确写法。
- 只附「大概率要」的：附件本身要计入每步重发的成本。
- 检查：在评测记录里找「工具调用后紧跟一次读取或探路命令」的模式，它就是该附在上一步结果里的东西。

## 3. 给事实和能力，不规定顺序

说明写清每层能拿到什么、准确到什么程度、代价与限制；不写「先做 A，再做 B」。

- 只把模型自己做不到或容易做错的写成规则：溯源要记什么、冲突不替用户选、坐标轴怎么对应、读不到的内容如实说明。
- 「必须先读某文档」这类句子先问：不读会错在哪？能否改成结果里的提示，在真正需要时出现？
- 检查：逐句问「删掉它，模型会做错什么？」答不出就删。

## 4. 前缀冻结，只在尾部追加

系统段、工具定义、Skill 索引与已有结果是缓存前缀；任何额外的模型调用（交接、封存、标题、重试）都沿用它，只在尾部追加，并用同一模型绑定。

- 动态内容（时间、计数、状态）放进尾部的消息或结果，不放进前缀。
- 改动前缀或另起请求的设计，要写明缓存代价。

## 5. 失败分类与错误文字

- 事实、权限、隔离类失败：失败关闭，不退回不安全的路径。
- 附带能力（预览、索引、投影、记忆）失败：降级，记诊断，主结果照常返回。
- 错误归类要准：「太大」不能报成「路径错误」，否则模型会去查路径。错误里用模型看到的路径，不暴露内部路径，并给出可执行的下一步。

## 6. 顺着模型习惯

模型会按训练里的常见做法行事（`ls`、`file`、转换工具、常用库）。让这些习惯得到正确结果，而不是一律拦截：例如常用转换命令返回已预处理的结果，常用库读大文件时自动改走轻量版本，并在结果里说明。

## 7. 改文字先测

改工具说明、结果文字、Skill 或系统段，都按同一流程：

1. 现状上跑基线，逐步复盘：哪些步是无效的（失败调用、探路命令、重复读同一内容、被拒的操作）。
2. 只改一类东西，同 seed 对照；结构改动与文字改动分开测，才能知道效果来自哪里。
3. 评测只判结果，不发明产品没有的上限；步数、输入 token、无效步数照常报告。
4. 多个不同场景各跑一次，胜过同一场景重复多次；客户数据不进仓库，夹具用脚本生成。

## 评审清单

- 典型任务的步数表（现在 / 改后）与每步重发量。
- 每层结果的末行是否说明下一层怎么拿。
- 新增句子各自防的是哪种错误。
- 前缀是否变化；变化的缓存代价。
- 失败属于哪一类，错误文字是否给出下一步。
- 对照评测的数字：结果、步数、输入 token、无效步。
