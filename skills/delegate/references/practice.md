# 续接、返工与并行写入建议

以下来自实际使用，是建议而非规则，按具体情况取舍。

`reply --when-done` 即时读取 stdin/文件与选项，独立后台 worker 等本轮结束后续答，shell 退出不影响；status 的 `pendingReply` 可见，stop 取消。不与 `--wait` 同用，重复排队拒绝，投递失败保留 `error`，apply 保留待续答，普通 clean/过期清理不删它（force 除外）；不保证机器重启或 worker 被杀后自动恢复。

- **续接还是新开**：返工建立在它已有理解上（审查意见、补测试）时用 `reply`；仍在运行时用 `reply --when-done` 先存一条补充、结束后后台续答（status 可见，stop 取消）；会话很长、答复开始畸形或方向已变时 `--fresh` 更好。worktree 是启动时的快照，之后你在自己工作区的改动它看不到，用 `reply --sync` 同步进去。
- **什么时候自己改**：根因已定位、改动小、你清楚怎么改时，自己改常常更快——派发、等待、审查、合并有固定开销。需要只有你知道的背景时也自己接手。
- **返工预算**：写入对话默认只给同事 1 次返工（`.delegate.json` 的 `maxRework`，`null` 不限），第二次 `reply` 会被拒绝（退出码 2）——这时 `diff --total` / `apply` 后自己改。上一轮为 `timeout`、`stalled` 或 `stopped` 的 `reply` 是续做，不计返工次数，即使预算已用完也可继续，meta 记 `continuation: <上一轮状态>`；其他失败仍按原规则计数。短修正（改名、补一处断言，说明 ≤600 字）用 `reply --minor`，不计次数，但该轮改动超过 60 行会补记一次；确需越限用 `--over-limit '<原因>'`，原因记在 meta。零改动的追问不计次。
- **用途与模型分开**：侦察用 scout、严密审查用 review、实现用 write；需要不同模型交叉审查时，用两个已登记的 `--model <别名>` 分路，由主控合并结论。界面实现也用 write，截图评审用只读 review；合并前扫静默吞错和夸大的验收结论。
- **让错误当场暴露**：审查说明给重点并注明不限于此，给待证伪的假设而不是结论；要求现状断言附 `文件:行号`、仓库外事实（配置键、CLI 参数、API 字段、版本号）附一手出处——模型会编出看似合理的名字。看图审查把影响判断的真实数据写进说明，并要求写明从图上哪里读出。
- **开几路**：写入 3–4 路最划算，瓶颈是主控审 diff 和跨路一致性；同事的时间多半花在等模型（实测占一轮的 50–70%），CPU 大部分时间空闲，路数不必压低；重检查都走 `lane`，几次编译撞在一起才会短时跑满；先提交共用基础（公共组件、约定），说明其误用方式；单路一个子系统、约 15 个文件以内。只读侦察可再并行几路。主控重检查也走 `lane`，避免 CPU 超卖拖过超时。
- **界面任务**：设计稿不委派，由你画完定稿；结构、文案原文、各状态的行为和要复用的现成样式由你定并写进说明，同事做接线、文案键、夹具与用例；验收用前端检查加指定用例，截图由你看。要看一眼才能判断好坏的（新布局、新视觉对象、动效）不派。
- **并行写入**：用 `--protect-reason model_loop.rs '另一任务负责；恢复逻辑必须留在这里'` 划清所有权（原 `--protect` 仍可用）；同事需要改受保护路径时须停下报告，不得搬逻辑或削弱测试绕路。同仓库串行 `apply`；新增 `NNNN_` 文件的编号冲突会警告，由你审查和改号。重写、迁移类任务把测试也保护起来，免得“改测试”成为最省事的通过方式；任务测试用 `--accept-also` 保留默认门禁，worktree 跑不了全量时至少跑相关 gate；多路合并的类型漂移只在合并后暴露：`apply A B …` 合完一批后在主干重跑一次验收没法沿用的任务各自的验收（结论 `verify`，失败退出 1；`--verify` / `--no-verify`，`applyVerify: false` 关闭），慢 apply 放后台；全量门禁仍按批自己跑。`start` 发现同仓库仍在运行的写入任务会在 stderr 列出其已改文件，任务说明点名其中路径时以 `overlap:` 提示，考虑 `--after` 或 `--protect`。
- **编排**：常用两种——write 实现后接 `--after impl --in impl --read-only` 的 review 预审（你拿着预审看 diff）；scout 侦察后接 `--after scout --worktree` 的 write 按清单实现。链条不宜太长，每多一步误差叠加一次，需要判断的节点你插进来看。
- **验收管住实质**：写入模型会朝验收命令收敛。只查 fmt/clippy 时，它交过一个只跑 `SELECT 1`、用 `true` 冒充 sandbox 的“压测”并通过验收；说明里写“未达标继续定位”时，它仍在未达标时交付。把指标写进验收脚本（不达标退出非 0，让 delegate 自动拒收），测量类任务再断言确实走了真实路径（写入的事件数、启动的 sandbox 数、连接峰值等）。
- **根因不明先诊断**：失败原因不清楚时，先派只读诊断，要求根因附提交、`文件:行号` 和与决策文档的对照，你确认后再派修复。直接派“修好它”，写入模型容易把测试改到通过并给出看似合理的解释；一次真实经历是同一个失败测试来回 4 轮。根因清楚但涉及设计取舍的小修，自己改通常更快。
- **审正确性也审代价**：修复可能把成本放到热路径上（例如每次请求扫描全部历史记录的大字段）。说明里要求同事写出新增查询或扫描的代价与所在路径；审 diff 时先问“这条路径多久跑一次、数据会长到多大”。
- **测量预约**：压测、计时、编译耗时这类结果会被并行编译污染（同一组数据库测试从 2.5–5 分钟拖到 13 分钟）。使用 `lane --measure` 或配置 `measure` 前缀自动预约核；预约之间 FIFO 排队，排队时间不计 stall/timeout，并记录核数与负载。
- **编译型仓库的一轮慢在编译**：看 run 目录的 `events.jsonl`，`bash`→`bash_done` 之和是命令时间，`bash_done`→下一个 `turn` 近似模型时间。一次 Rust 写入任务 84 分钟里命令占 72 分钟、模型约 12 分钟，没有排队：每改一处就编一次（约 30 次），且在 `cargo build`、`cargo test --no-run`、`clippy` 之间来回换（三套产物各自重编）。在 `standing.write` 写“攒一组修改再编；中途只用 `cargo clippy -p <crate> --all-targets`；测试改完再跑”，并用 `agentDeny` 拦 `cargo build`（hint 指向 clippy）。只读任务在冷 worktree 里同样会为了验证结论去编译，`standing.readOnly` 写明默认不编译、需要运行结果时把命令写进答复。
- **缩短每一轮**：一轮的大头是同事读代码、想方案的时间，说明里给到根因、`文件:行号` 和设计取舍时明显变短（同一任务续做时模型时间从约 60 分钟降到约 20 分钟）；返工一轮的代价通常是 40–70 分钟，比多写几句说明贵得多。需要反复跑的测量（压测、基准）给同事一个只跑单档或单个场景的入口，迭代时不必每次跑全套。
