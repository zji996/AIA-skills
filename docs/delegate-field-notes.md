# delegate 实战记录

> 在真实任务中使用 delegate 时发现的问题、做法与数据，供改进本技能与设计 agent harness 参考。
> 不在技能目录内，技能加载时不会读取。按主题归类；每条写现象、原因、处理，以及对 harness 的启示。
> 来源：2026-09-26 至 09-29 在 video-shard-studio、image-shard-studio（ISS）与本仓库的连续使用（lane、Rust 迁移、packing 修复、ISS 前端迁移与动效统一等）。
> 表格里的“待改进”只标仍未做的；已做的改为“已解决（版本）”，完整清单见文末。

## 一、隔离与归属

| 现象 | 原因 | 处理 | 对 harness 的启示 |
|---|---|---|---|
| 只读审查找出了真实缺陷，却因主控同时编辑被判 `failed` | 原地运行，快照差异无法区分是谁改的 | 只读默认在 worktree 快照中运行；state 只描述答复，工作区核验另列（4.3） | **归属必须靠隔离，不能靠事后推断**。并行 agent 默认各自一份快照 |
| 旁边另一个 agent（Kilo）同时改同一仓库 | 多 agent 共享工作区是常态 | 同上；写入任务用 `--worktree` | harness 应把"谁在改哪个工作区"当一等状态 |
| 只读 worktree 把未提交的子模块指针误报为违规 | 为让 `git diff HEAD` 可见改动做了 mixed reset，index 被重置 | 改 `reset --soft`（5.0.1） | 快照语义要端到端测试，尤其是子模块、大文件、符号链接这些边角 |
| 同事为跑测试初始化子模块，改动清单出现 `submodule contents`，`apply` 会冲突 | 子模块在 worktree 中是空目录，同事自行补齐 | 每次合并前手动 `git submodule deinit -f`（发生 4 次） | **已解决（5.1.0）**：apply 默认忽略"仅初始化"的子模块变化 |
| 只读 worktree 里看不到 ISS 子模块源码 | 子模块未链接 | 任务说明里给绝对路径 | `.delegate.json` 的 `link` 应覆盖审查常用的参考子模块 |

## 二、档位与同事能力

| 现象 | 原因 | 处理 | 启示 |
|---|---|---|---|
| 派给便宜档 Pi 的"看这轮改了什么"审查只能看到现状 | 只读 Pi 被砍掉 shell，跑不了 git | 能隔离时不再限制 Pi 的工具（5.0.1）；无法隔离时才限制 | **工具限制与隔离是替代关系**：有隔离加事后核对，就不必再阉割能力 |
| 上述情况不会自动升档 | Pi 给出了看似正常的答复，state 是 `answered` | 主控靠读结果发现 | 升档只能兜住"失败"，兜不住"答得浅"；主控审查不可省 |
| 按"同事性格表"挑人，实际几乎只用 Codex | 路由判断全压在主控身上 | 改为按任务类型选档位，只读默认便宜、写入默认强（4.5） | 路由应是配置加规则，模型只声明任务类型 |
| 嵌套委派带来了一串复杂度与 bug（`LANE_HELD` 泄漏、父 run 豁免） | 任务里再起任务 | 只保留一层（4.5） | 与人类组织相同：层级是为弥补注意力不足；agent 的注意力可外置到文件，应更扁平 |

## 三、验收与审查

| 现象 | 原因 | 处理 | 启示 |
|---|---|---|---|
| `delivered` 的 Rust 首版仍有 6 处问题（非 UTF-8 行停读、三处轮询、竞态、PID 复用） | 验收只证明测试通过；测试没覆盖这些 | 主控审 diff，把漏洞补成测试再返工 | **"验收通过"不等于"改对了"**。追踪主控审查率 |
| 重写任务最省事的"通过"方式是改测试 | 目标与手段错位 | 验收命令里加 `git diff --quiet HEAD -- tests/ docs/spec.md` | **已解决（5.1.0）**：内建 `--protect <路径>`，受保护路径被改即判失败 |
| 独立审查每次都找到作者自测没发现的问题（lane 5 处、packing 2 处回归、Rust 首版 6 处） | 作者盲点；换模型家族更有效 | 关键路径固定走"实现、换家族审查、主控裁决" | harness 默认给写入任务配一个只读审查者 |
| `make check` 通过，却漏掉"没装可选依赖时导入失败" | 本机依赖齐全；环境单一 | 让同事加"屏蔽依赖后导入"的回归测试 | 审查者应被要求思考"检查环境之外"的部署形态 |
| 契约测试全过，但 `--help` 不可用、状态行字段按字母排、`diff --` 不支持 | 契约测试只测行为，不测"人和模型怎么用" | 补易用性用例（5.0.1） | 除契约测试外还需要**易用性测试**：帮助、错误信息、输出可读性 |
| agent-handoff 按带空格的文本 grep `meta.json`，Rust 写紧凑 JSON 后漏报 | 两个技能之间的隐式契约 | 规格写明 JSON 空白与顺序不属于契约；handoff 容忍任意空白 | 跨组件的数据格式要写进契约并有测试 |

## 四、等待、通知与多仓库

| 现象 | 原因 | 处理 | 启示 |
|---|---|---|---|
| 反复用 `status` 轮询 | 不知道可以后台等待 | SKILL.md：放一个后台 `wait`，等通知 | 完成通知应是 harness 的原生能力 |
| 用 `&` 放后台的 `wait` 结束时没有通知 | 只有 harness 自己的后台机制才会回调 | 用 harness 的后台运行 | 同上 |
| 在 A 仓库起的后台 `wait` 收不到 B 仓库的任务 | run 记录按调用目录的 git 根存放 | 每个仓库各放一个 `wait` | **已解决**：5.3.0 `wait --machine` 按整机收取；5.8.0 无参 `wait` 按调用者会话收取 |
| 不带参数的后台 `wait` 收不到它启动之后才派发的任务 | `wait` 在启动时确定要等的任务集合 | 新派的任务再放一个 `wait` | 动态收取要防止任务持续派发时永不结束；harness 更适合按任务事件逐个推送，而不是一次性等全部 |
| 高负载下测试偶发失败（固定 `sleep 0.3` 后断言） | 时序假设 | 改为"等到条件满足" | 测试与编排都不应依赖固定时长 |

## 五、任务说明

| 现象 | 处理 | 启示 |
|---|---|---|
| 说明里写"看 `git diff HEAD`"，但只读 worktree 的 HEAD 是快照提交，同事绕了一圈 | 修正快照 HEAD 语义；说明里只写事实 | 说明里的操作指引要与工具的真实行为一致，否则比不写更糟 |
| 我在一份说明里先要求改规格、又改口禁止，矛盾留在了说明里 | 说明写完先自读一遍 | **待改进**：可用便宜档先审一遍任务说明（是否自足、是否矛盾） |
| 先由主控定位根因、写清约束，再交给强档实现，几分钟就完成（lane 死锁 7 分钟） | 固定为"主控诊断、同事实现、主控审方向" | 瓶颈在说明质量，不在同事能力 |

## 七、Pi 与 Codex 同题对比（ISS 前端迁移审查，任务说明一字不差）

| 维度 | Pi（Gemini flash，5.0.1 起在 worktree 中有全部工具） | Codex（GPT） |
|---|---|---|
| 耗时 | 296 秒，63 轮，57 次 shell | 222 秒 |
| token | 输入约 353 万（缓存 322 万，新读入约 32 万），输出 3.4 万 | 输入约 81 万（缓存 71 万，新读入约 10 万），输出 0.9 万 |
| 覆盖 | 16 行，按提交逐组列全，含后台接入尺度、遗留样式清理顺序、页头运行状态点 | 11 行，集中在有判断价值的项 |
| 落到 VSS 代码的具体发现 | 更多：三个开关控件各复制一份、会话侧栏固定 176px、Ref2VA 用原生复选框与带强转的原生下拉（均核实属实） | 较少，但每条都准 |
| 事实错误 | 1 处：把原生 `<select>` 说成 `GlassSelect` 的现有用法（建议本身正确） | 未发现 |
| 风险意识 | 较弱，语气笃定（"极高收益""丑陋"），很少写"待确认" | 强：每项写出具体副作用（删除按钮辨识度、动画结束事件、面板高度与焦点） |
| 前三项 | 单按钮采用、GlassSelect 泛型与防裁切、开关与复选框统一 | 单按钮采用、GlassSelect 键盘、会话列表搜索与删除确认 |

结论：
- 前端/界面类审查，放开工具后的 Pi 已经可用，**发现面甚至更广**；但要核实，且篇幅冗长、措辞偏营销。
- 两者并集明显好于任一方：Pi 找到更多具体的代码事实，Codex 更准、风险意识更强。重要审查值得两路并行、主控合并。
- 升档兜不住"答得浅"，同样兜不住"答得不准"：**要求每条现状断言附 `文件:行号` 证据**，能让这类混淆当场暴露；已写进 recipes 的任务说明模板。
- Pi 的输出应限定篇幅与语气（表格加前三项，不用形容词），否则主控的阅读成本抵消了它省下的钱。

### Pi 的写入任务（ISS 会话列表迁移，便宜档独立完成）

- 结果：`delivered`，`make check` 通过，新增 8 项测试、+894/−94 行；22 分钟；新读入约 82 万 token（缓存 1355 万），输出约 7.9 万。同期 Codex 的前端 A 组（32 个文件）用了 23 分钟。
- 质量：交互实现完整（搜索、删除二次确认的 350 ms 生效与 3.5 s 自动取消、失败回滚、Escape 优先收起）。遵守了"拿不到状态就照实说明、不要自造轮询"的约束，如实写明关闭面板后状态点失效的原因。
- 遗漏：旧的侧栏组件没删，成了死代码，审查时由主控删除（小改动，自己改更快）。
- 结论：界面类写入交给放开工具的 Pi 可行；输出偏长、token 偏多，但单价低。给它的说明里把"不要做什么"写清楚很有效。

| 现象 | 处理 | 启示 |
|---|---|---|
| Rust 首版交付后，6 条审查意见用 `reply` 发回，14 分钟改完 | 返工建立在它已有理解上时用 `reply` | 续接会话省掉重新读材料 |

## 九、编排首次实战（5.2.0）

| 现象 | 处理 | 启示 |
|---|---|---|
| Pi 完成设计尺度第一阶段后，用 `--in` 让 Codex 在它的 worktree 快照里审查，4 分钟给出 5 条意见 | 4 条属实（移动端触控区从 44px 缩到 24/32px、间距与高度 token 只写在注释里、徽标颜色未引用 token、文档与实现不符），交回 Pi 在原会话返工 | "便宜档实现、强档审查"有效：Pi 自己测试全过、答复写得很满，但触控回归这种问题只有换一个视角才看得出来 |
| 第 5 条（P1）是假问题：子模块在审查者眼里变成了指向本机的符号链接 | 追查发现是 `--in` 快照没有排除上游的 link 路径，5.2.1 修复 | 新功能第一次上真实任务就暴露边角；工具的 bug 会伪装成被审代码的问题，主控要能分辨 |
| 一段对话的第一轮已合并提交，第二轮改了第一轮新加的行，再次 `apply` 整体冲突、什么都没写 | 用第二轮自己的 `changes.patch` 配合 `git apply --3way` 绕过；5.2.1 改为以"上次已合并的状态"为基准 | "续接对话"和"分轮合并"是同一个工作流的两半，两者的状态必须一起设计 |
| Pi 审 Codex 写的权重清理代码（会删模型文件），逐项核对并发、锁顺序、断点恢复，结论"未发现会误删的路径"，附 8 行核对表 | 采纳，合并 | 换家族审查对高风险代码很值：便宜档也能给出扎实的安全核对，前提是说明里只问一个明确的问题 |
| 设计第二阶段：Pi 又把移动端触控区缩到 32～40px，而第一阶段刚修过同类问题、44px 下限也已写进 Pi 自己写的设计文档 | 返工说明里给出可执行的自查方法（列出所有可点击元素逐个核对，并报告排查数量），而不只是列问题 | 便宜档不太会把一条约束推广到新场景；要么给它可执行的检查清单，要么把约束写成自动检查（例如测试或 lint），不能只靠文档 |
| 用 `--after` + `--in` 一次声明"Pi 实现 → Codex 审查"，审查在 Pi 结束后自动开始，等待期间状态为 `waiting`、不占名额 | 主控只在两步都结束后看一次 | 编排省掉了主控中途传话的一轮；但审查任务启动时用的是当时安装的版本，工具升级不影响已在等待的任务 |
| 设计第三阶段（最容易改坏的高密度区域）：说明里把"不许动什么"逐项列出，并要求答复"列出你刻意没动的地方"；Pi 这次没碰任何布局计算，Codex 审查也确认了这点，只剩 3 个小问题 | 采纳这种写法；剩下的小问题主控自己修 | 对便宜档，明确的否定清单加"报告你没做什么"比笼统的"不要改布局"有效得多 |
| 5.2.1 修好 `--in` 后，同一流水线的审查不再报假的子模块问题 | — | 工具修复要在下一次真实使用里确认生效 |
| 同一对话前后几轮分别用不同版本的 delegate 合并（旧版没有记录合并基准），新版 `apply` 仍会按对话起点合并而冲突 | 用该轮自己的 `changes.patch` 加 `git apply --3way` | 升级跨越"状态格式变化"时，进行中的对话需要一次性的兼容路径或明确的说明 |
| Pi 的答复 8800 字，对照表很完整但主控只需要结论 | 返工时要求"答复简短、逐条附 文件:行号、不重复对照表" | 在说明里直接规定答复的形式，比事后抱怨有效 |
| ISS 收尾核对时发现仓库里残留两条 prunable 的 worktree 登记：先 `clean` 上游、再 `clean` `--in` 审查者，后者按记录的来源（已删除的上游 worktree）去 prune，找不到仓库 | 手动 `git worktree prune`；5.3.1 改为按 worktree 自身的 common dir 定位仓库 | 收尾时核对 `git worktree list`；回归测试要覆盖不同的清理顺序，只测一种顺序会直接通过 |

## 十、主控与同事并行改同一前端（ISS 训练动线，2026-09-28）

| 现象 | 处理 | 启示 |
|---|---|---|
| Codex 在 worktree 里做后端 + 契约 + 前端删分支，主控同时在主工作区重做页面动线；`--protect` 划出主控独占的 10 个文件 | Codex 60 分钟内交付，`make check` 与隔离库集成测试通过；`apply` 对主控已改动的文案与测试文件自动三方合并，零冲突 | 按文件划分所有权加 `--protect`，前后端可以真正并行；重叠的文案文件只要双方各自追加或删除、不重排，合并就是干净的 |

## 十一、只读侦察与看图审查（ISS 训练首页比例与动效，2026-09-28）

| 现象 | 原因 | 处理 | 启示 |
