## 门禁等待与改写合入（2026-10-03）

polaris-os 主控用 `until ! pgrep -f scripts/gate.sh` 等门禁，模式匹配轮询 shell 自己，空转近 5 小时；后台直接跑命令本身或 lane。
同事改动改写后手动合入只显示部分包含，16 个 worktree 长期未清；自动检测只认完全包含，提交后立即 `clean <run> --force`。

## 源仓库构建缓存（2026-10-08）

polaris-os 的 `target` 涨到 155 GiB：增量编译目录 107 GiB（564 个会话目录），工作区自有 crate 的旧哈希产物 33 GiB（1,215 个文件，全部产生于一周内）。
删掉这两类后剩 19 GiB，磁盘已用从 515 GiB 降到 378 GiB；之后单个 crate 的测试重编在一分钟内。
“7 天前的一律删”只能筛出 3.7 GiB 且多是仍有效的第三方库；按访问时间筛出 0 个（relatime）。有效条件是“名字属于工作区 + 早于最近一次全量构建”。
同事构建已设 `CARGO_INCREMENTAL=0`；这些都在源仓库的 `target` 里，由主控自己的构建与门禁写入，worktree 提示覆盖不到。

## 仍有指导意义的经验

### 隔离与审查边界

- 隔离决定归属：其他 Agent 与主控同时编辑很常见，写入用 worktree；harness 应记录谁在改哪个工作区。
  有隔离和事后核对时可给完整工具；只读不是权限沙箱。参考子模块源码通过仓库 link 配置提供。

- 验收通过仍需审 diff：Rust 首版 delivered 后发现非 UTF-8 停读、轮询、竞态和 PID 复用等 6 处问题。
  漏洞补成测试再返工；关键路径换模型家族审查，考虑可选依赖缺失等部署形态。

- 新能力在真实任务中复核：in 的 link 假改动和分轮 apply 冲突都在首次实战暴露。
  工具 bug 会伪装成被审代码的问题；子模块、大文件、符号链接及不同清理顺序需端到端验证。

- 跨版本续接须核对状态：旧版没有合入基准时，新版仍可能从对话起点合并。
  曾用该轮 changes.patch 加 git apply --3way 绕过；跨状态格式升级需要兼容说明，修复也要部署到实际二进制。

### 任务说明与粒度

- 说明须自足且不矛盾：曾先要求改规格又禁止修改，操作指引也可能与快照 HEAD 语义不符。
  写完自读，给目标、范围、完成标准和已定事实；主控定位根因后再派实现通常更快。

- 审查写待证伪假设：要求文件:行号，区分事实、建议和可疑需确认，仓库外参数或配置键附一手出处。
  便宜档曾混淆组件名或夸大错误概率；正常 answered 不会升档，关键结论派修前由主控核实。

- 写入分 3–4 路较可控，单路一个子系统、约 15 个文件以内；27 文件的一路曾超时，reply 170 秒收尾。
  公共原语先提交并说明误用方式；曾多路遗漏退场重开实例状态，合并后才暴露。跨路共性需独立审查。

- 小修自己做：已定位的一行改动也派发，等待、审查和合并多花十几分钟。
  已有理解上的返工用 reply，长会话畸形或方向变化用 fresh；主控新材料用 sync，不让同事重读整轮。

- 开放式清单给判定标准：“以及 grep 找到的其他容器”曾让 22 处无外框按钮组都被加框。
  给明确清单和可检查的边界；便宜档未必把约束推广到新场景，重复问题宜变自动检查。

- 保护须说明原因：同事曾把“不能改”理解成可以搬逻辑绕路。
  互相 protect 划分所有权，版本、CHANGELOG、发布留主控；需要受保护修改时停下报告。

- 范围外整理需拦：同事为消除警告移动 SKILL 整节且未报告，主控撤回。
  已定公式、格式、兼容策略写进说明；审 diff 专看额外移动与删除，“门禁变绿”不构成范围授权。

### 合入与验收

- 各路验收是各自快照：新增 DTO 字段后主干 tsc 因另一路夹具缺字段失败；入口删除也使旧导航测试失效。
  共享 DTO 先合并再派依赖任务，说明会消失的入口；每批合入后主控跑全量。

- 外部状态也需隔离：migration 编号改正后，17 个用例仍因共享数据库残留失败。
  独立库/schema 由仓库测试入口提供；迁移任务准备可清空的库，运行库彩排用副本，基准与门禁分库。

- 负载放大时序假设：同步断言异步分页偶发失败，单独连跑三次通过后改异步等待。
  rejected 先看关联性，墙钟断言先单独重跑；用条件等待替代固定 sleep，确定门禁与模型评测分开。

- changes 为 0 不等于对话没改动：reply 只跑验收时曾被误解为无需 apply。
  diff --total 和 pendingChanges 看累计改动；任务名与旧 run id 都指向最新轮，不必另找原 id。

- 证据在 clean 前取走：忽略目录中的截图和复验脚本不随 apply 合入，清理后丢失。
  同事给证据位置并保存截图脚本；主控先归档再清理，不在公开记录复制机器私有路径。

### 等待与长时间推进

- 通知用宿主后台机制：shell 的 & 曾没有通知；派出任务后不能不挂等待就结束会话。
  逐行通知用 stream，结束通知循环 any；动态派发确认新任务被覆盖，Monitor 到期重挂。

- 压缩后旧 waiter 仍占任务：再次 wait 返回 76，三个任务通知落在旧上下文。
  先 status --json 核对结局与等待者，再 result/apply 已结束任务；76 不表示完成。

- 持久待办使推进可续接：忽略目录记进行中、待做、待确认，每轮更新。
  只读审计留请求、id、代码行，优先修阻塞再复走；唤醒、停止与授权见 [long-run.md](../skills/delegate/references/long-run.md)。

### 失败语义与界面审查

- 新旁路写失败分级：记忆去重、钩子错误曾使封存或 Run 失败，强档把“失败关闭”推广到所有路径。
  入口明确安全、权限、事实失败关闭，投影、索引等附带能力只作诊断；提供统一挂点，说明补失败语义。

- 降级与取消成对核对：Cancelled 曾被当普通错误吞掉，结构兜底又把 usage/Ledger 写入混进降级块。
  强档复审 8 个提交，6 条假设，约 5 分钟证实 4 条、证伪 3 条，每条附行号和最小修复。
  问取消能否到调用方、降级块是否包含事实写入；Host 侧附带步骤也要覆盖。

- 便宜档事实清单广，严密判断需核实：同题 Pi 多找到 UI 问题，但曾误认组件与 inert 语义。
  强档缺陷带复现和风险；重要审查两路由主控合并，Pi 输出限定表格与前三项。

- 看图给真实分布：Pi 曾误判 grid 等高卡片错位，又忽略图片中位宽高比 0.71，推荐裁切更重的 3:2 封面。
  附真实数据，要求断言说明从哪里读出、量到多少；侦察与看图并行，结论作待验证假设。

- UI 交付核截图与代码：Pi 完整实现搜索、确认、回滚和 Escape，却留死组件；另一任务空 catch 且自称全覆盖。
  合并前扫吞错、答复数字以 diff 为准；触控区等重复约束提供可执行自查或 lint。

- 动效单测不能证明观感：真实截图暴露面板塌缩、滚动条空槽、新旧页叠加，同事却报告稳定。
  要关键元素改前/后坐标并核截图，联动动画说明两侧同曲线同时长；主控取舍后逐帧复验。
